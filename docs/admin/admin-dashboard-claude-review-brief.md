# 관리자 페이지 로컬 구현 검수 요청 브리프

작성일: 2026-07-06  
대상: Claude 검수용  
브랜치: `feat/admin-dashboard-shell`  
상태: 로컬 구현 진행 중. push, PR, merge 아직 하지 않음.

## 1. 이 문서를 보는 이유

Claude와 마지막으로 논의했던 지점은 팀장님 답장 해석이었다.

팀장님 답장 요지:

```text
p2,p3 구분 없이 관리자 페이지를 확장해 나가면 됩니다.
AI가 p2,p3라서 축소하려고 해도 phase 나누지 말고 페이지 기능을 만들라고 하시면 됩니다.
그리고 최소 관리자 화면이 아니라 관리자 화면에서 필수 기능이 규태님이 보내주신 항목이 맞는지도 확인 부탁드립니다.

1. 관리자 대시보드
2. 상품 조회/상태 확인
3. 엑셀 기반 상품 대량 등록
4. 파일명 기반 이미지 대량 연결
5. 성분 매핑 검수
6. 재고/가격/주문 상태 확인
```

Claude의 당시 해석:

- 관리자 페이지에 한해서 P2/P3 phase 라벨을 제거한다.
- 필수 기능은 팀장님이 적은 6개가 맞다.
- 단건 상품 등록/수정은 엑셀 없이 한 건을 바로 보정할 때 필요하므로 추가 제안할 만하다.
- 관리자 화면 구현은 규태 쪽에서 진행해도 되는 흐름으로 해석할 수 있다.
- 다만 백엔드 API, import job, 재고/주문 실제 저장은 원우님 영역과 맞춰야 한다.
- OCR 자동 확정 금지, 정규화 exact match만 자동, pending 검수 같은 안전 규칙은 phase와 무관하게 유지해야 한다.

이후 Codex가 위 해석에 따라 관리자 화면 로컬 프로토타입을 계속 발전시켰다.  
이 문서는 그 결과물을 Claude에게 거의 빠짐없이 넘기고, 방향과 범위를 다시 검수받기 위한 자료다.

## 3. 핵심 구현 요약

### 3.1 `/admin` 라우트

`/admin` 경로가 관리자 화면으로 연결되어 있다.

또한 사용자용 플로팅 에이전트 버튼이 관리자 화면에 뜨면 운영 화면을 가리므로, `/admin`에서는 숨기도록 처리했다.

```tsx
if (appMode === "community" || location.pathname.startsWith("/admin")) {
  return null;
}
```

### 3.2 디자인 시스템 적용

팀에서 받은 관리자/프로젝트 색상 토큰을 기준으로 화면을 구성했다.

```text
Ink / Navy:     #0B2A3A
Accent / Mint:  #94E0F8
Accent 2:       #5EC6E8
App BG:         #ECEFF3
White:          #FFFFFF
Line:           #E6E9EE
Muted:          #8A93A0
Text:           #25313F
```

화면 톤은 쇼핑몰 운영자가 반복적으로 보는 업무 화면에 맞춰, 과한 랜딩 페이지식 히어로나 장식을 피하고 정보 밀도를 높이는 방향으로 잡았다.

## 5. 필수 기능별 구현 내용

### 5.1 관리자 대시보드

구현된 내용:

- 전체 상품, 추천 가능, 판매중, 검수 필요, 품절 임박, 이미지 누락, 전성분 원문, 인덱스 대기 지표
- 팀장님 필수 기능 6개 체크 카드
- 각 카드 클릭 시 해당 메뉴로 이동
- 오늘 처리할 일 목록
- 최근 import job 결과
- 운영 액션 로그
- 주문/결제 오늘 요약
- 검색/추천 인덱스 상태
- 자동 등록 운영 흐름
- 실제 API/job 연결 필요 항목 체크리스트
- API 연동 목록 CSV 다운로드
- 자동 rebuild 상태
- 성분 정책 요약

추가된 실사용 느낌:

- 대시보드의 처리 대기 항목을 누르면 관련 화면으로 이동한다.
- 화면 조작 시 최근 운영 로그가 갱신된다.
- API 연동 체크리스트를 `mwbl_admin_api_handoff.csv`로 다운로드할 수 있다.

### 5.2 상품 조회/상태 확인

구현된 내용:

- 상품명, 브랜드, 상품코드 검색
- 판매 상태 필터
- 상품별 가격, 재고, 판매 상태, 검수 상태, 이미지 수, 성분 상태, 검색 반영 상태 표시
- 상품 행 클릭 시 단건 상품 등록/수정 화면으로 이동
- 신규 상품 등록 버튼

운영 목적:

- 셀러가 등록한 상품이 판매 가능 상태인지, 이미지/성분/인덱스 반영 상태가 정상인지 빠르게 보는 화면이다.

### 5.3 단건 상품 등록/수정

팀장님 목록에는 없었지만 Claude가 추가 제안했던 항목이다.

구현된 내용:

- 상품명
- 브랜드
- 상품코드
- 판매가
- 재고
- 판매 상태
- 이미지 수
- 전성분 원문 전체 입력
- 전성분 정규화 exact match 미리보기
- exact/pending 카운트
- 로컬 저장

성분 입력 미리보기:

- 내부 canonical 성분 샘플과 정규화 exact match되는 항목은 `exact`
- 나머지는 `pending`
- 부분일치 자동 확정은 하지 않는다.

현재 canonical 샘플:

```text
정제수
부틸렌글라이콜
글리세린
나이아신아마이드
판테놀
소듐하이알루로네이트
세라마이드엔피
병풀추출물
자작나무수액
```

중요:

- 지금은 실제 `ingredients.csv`를 직접 읽는 구현은 아니다.
- 화면 동작과 정책을 보여주는 로컬 프로토타입이다.
- 실제 연결 단계에서는 내부 `ingredients.csv` canonical 기준으로 바꿔야 한다.

### 5.4 엑셀 기반 상품 대량 등록

구현된 내용:

- 파일 선택 UI
- 템플릿 컬럼 안내
- 템플릿 CSV 다운로드
- 검증 실행 버튼
- 검증 후 성공/실패 요약
- 실패 행 테이블
- 실패 파일 CSV 다운로드
- 상품 등록 대기열 추가
- import 후 rebuild 흐름 표시

다운로드되는 파일:

```text
mwbl_product_import_template.csv

```

정책:

- 성공 행은 커밋 가능

- rollback 전체 자동화는 아직 구현하지 않음
- import 완료 후 검색 문서 rebuild와 임베딩 반영이 필요함

주의:

- 실제 파일 파싱은 아직 없다.
- 지금은 업로드/검증/실패 결과 흐름을 보여주는 로컬 시뮬레이션이다.

### 5.5 파일명 기반 이미지 대량 연결

구현된 내용:

- 이미지 zip 또는 파일 묶음 선택
- 파일명 규칙 안내
- 이미지 매핑표 CSV 다운로드
- 매칭 실행
- 매칭 결과 요약
- 대표/상세 이미지 미리보기 카드
- 실패 행 테이블
- 실패 파일 CSV 다운로드
- 이미지 연결 대기열 추가

다운로드되는 파일:

```text
mwbl_image_mapping_template.csv
mwbl_image_match_failures.csv
```

자동 등록 가능 범위도 화면에 설명했다.

정리:

- 파일명/매핑표가 있으면 기존 상품 이미지 자동 연결 가능
- 엑셀 상품 정보와 이미지 파일명이 함께 있으면 상품 정보와 이미지 동시 등록 가능
- 이미지만 단독으로 상품 전체를 자동 생성하는 것은 위험
- 라벨/OCR은 자동 등록이 아니라 후보 추출과 검수 보조로 처리

### 5.6 OCR 후보 추출

팀장님이 "이미지 업로드를 해서 자동 등록까지 가능한지" 확인을 요청했으므로, 완전 자동 등록 대신 검수 보조 흐름을 넣었다.

구현된 내용:

- 이미지 매칭 후 `OCR 후보 추출` 버튼 표시
- OCR 후보 추출 시 후보 테이블 표시
- 상품명 후보
- 브랜드 후보
- 전성분 후보
- 가격/재고는 이미지 단독 추출 대상이 아니라고 표시

정책:

- OCR 결과는 자동 확정하지 않는다.
- 상품명/브랜드도 후보로 표시한다.
- 전성분은 pending 검수로 넘긴다.
- 가격/재고는 엑셀 또는 직접 입력이 필요하다고 둔다.

### 5.7 성분 매핑 검수

구현된 내용:

- pending 성분 후보 목록
- pending code
- raw name
- normalized name
- 등장 상품 수
- 연결 수
- suggested canonical
- confidence
- status
- 선택 성분 상세
- 승인
- pending 유지
- 반려
- 검수 저장
- 후보 CSV 다운로드

다운로드되는 파일:

```text
mwbl_pending_ingredient_candidates.csv
```

최근 개선:

- 성분 후보 상태가 로컬 state로 실제 변경된다.
- `승인`, `pending 유지`, `반려` 버튼을 누르면 행 status가 바뀐다.
- 변경된 status가 후보 CSV에 반영된다.

정책:

- 내부 `ingredients.csv` 기준 정규화 exact match만 자동 확정
- 부분일치, OCR, 복합 원료, 상표명은 pending 유지
- accepted alias 후보는 나중에 성분 alias 기준으로 반영
- 성분 alias를 실제로 확정하는 기준은 세민님 검수/데이터 계약과 맞춰야 함

### 5.8 재고·가격

구현된 내용:

- 상품별 판매가 수정
- 상품별 재고 수정
- 상품별 판매 상태 수정
- 선택 상품 상세
- 변경 사유 입력
- 수정 저장
- 변경 이력 테이블
- 변경 이력 CSV 다운로드
- 재고 화면 필터
  - 전체 상품
  - 품절/임박
  - 검수 필요
  - 판매중지
- 저재고 상품 일괄 판매중지
- 요약 지표가 현재 로컬 상품 상태 기준으로 갱신됨

다운로드되는 파일:

```text
mwbl_stock_price_changes.csv
```

최근 개선:

- `저재고 중지` 버튼을 누르면 재고 20개 이하 상품이 `판매중지`로 바뀐다.
- 변경 이력에 일괄 처리 기록이 남는다.
- 필터가 자동으로 `판매중지`로 바뀌어 결과가 바로 보인다.
- 수정 저장 시 변경 사유가 이력에 들어간다.

주의:

- 실제 상품 수정 API는 아직 연결하지 않았다.
- checkout preview와 주문 생성 시점에는 서버 기준 가격/재고 재검증이 필요하다.

### 5.9 주문·결제

구현된 내용:

- 최근 주문 목록
- 주문 상태 필터
- 결제 상태 필터
- 선택 주문 상세
- 결제 상태
- 추천 ID
- 예약 재고 수량
- 상태 새로고침
- 결제 만료
- 취소 승인
- 배송 준비
- 배송 시작
- 결제·재고 예외 테이블
- 주문 처리 기준
- 운영 정책

최근 개선:

- 주문 목록이 로컬 state로 관리된다.
- `결제 만료`를 누르면 결제대기 주문이 `만료`로 바뀌고 결제 상태는 `실패`, 예약 재고는 0으로 바뀐다.
- `취소 승인`을 누르면 취소요청 주문이 `취소완료`로 바뀌고 예약 재고는 0으로 바뀐다.
- `배송 준비`, `배송 시작`도 로컬 상태 전환이 된다.
- 액션 후 예외 이력과 운영 로그에 기록된다.
- 액션 후 바뀐 상태 필터로 자동 이동해 운영자가 결과를 바로 본다.
- 대시보드의 주문 요약도 현재 주문 state 기준으로 계산된다.

주의:

- 실제 주문/결제/재고 API 호출은 아직 없다.
- 원우님 API 계약에 맞춰 같은 버튼을 실제 API에 연결해야 한다.

## 6. 자동 rebuild와 임베딩 반영 표현

팀장님은 수동 rebuild가 아니라 자동화 방향을 원했다.

화면에서는 다음처럼 표현했다.

- 검색 문서 rebuild는 import 완료 후 즉시 job 방향
- 임베딩 반영은 서버 `OPENAI_API_KEY` 준비 전까지 일배치/운영자 실행
- 서버 키 확보 후 즉시 job으로 승격 가능
- 최근 full 반영은 24,585 / 24,585로 표시

주의:

- 실제 job 실행은 아직 구현하지 않았다.
- 실제 서버 키와 배치 실행 정책은 지운님/원우님과 맞춰야 한다.

## 7. API/job 연동 체크리스트

대시보드에 실제 연결 필요 항목을 정리했다.

현재 항목:

```text
상품 등록/수정: 상품 생성·수정 API, 중복 경고 응답
엑셀 import: 부분 성공 커밋, 실패 파일, import job ID
이미지 연결: 파일 업로드, storage_key 생성, 대표/상세 이미지 구분
성분 검수: 세민/데이터 계약 기준 canonical 확정, pending 유지, 반려 reason 저장
검색 반영: import 완료 후 search document rebuild, 변경분 임베딩
주문 확인: 주문 조회, 결제 상태, 예약 재고, 취소/만료/배송 상태 전이 규칙 원우 확인
관리자 접근 제어: /admin 라우트 권한 가드, auth 세션 admin role 확인
```

이 목록은 `연동 CSV` 버튼으로 내려받을 수 있다.

다운로드되는 파일:

```text
mwbl_admin_api_handoff.csv
```

## 9. 아직 구현하지 않은 것

아래는 의도적으로 아직 하지 않았다.

- 실제 DB 저장
- 실제 상품 생성/수정 API 호출
- 실제 엑셀 파일 파싱
- 실제 이미지 업로드
- 실제 OCR
- 실제 성분 alias DB 반영
- 실제 search document rebuild job 호출
- 실제 embedding batch 호출
- 실제 주문 상태 변경 API 호출
- 실제 결제/Toss API 호출
- 실제 관리자 권한/auth guard
- push
- PR
- merge

즉 현재 결과물은 "관리자 페이지 화면과 운영 흐름 로컬 프로토타입"이다.

## 10. Claude에게 검수받고 싶은 질문

아래 관점으로 검수해 달라.

### 10.1 팀장 지시 반영 여부

- 관리자 페이지에 한해서 P2/P3 phase 구분을 제거한 방향이 맞는가?
- 팀장님이 적은 필수 기능 6개가 화면상 충분히 반영됐는가?
- 단건 상품 등록/수정을 추가한 것이 타당한가?

### 10.2 범위 과잉 여부

- 현재 로컬 화면 구현이 규태/R4 업무 범위를 지나치게 넘었는가?
- 또는 팀장님 지시상 "관리자 화면을 기능 단위로 계속 만들라"는 범위 안에 들어가는가?
- 백엔드 API는 건드리지 않고 화면/mock만 만든 현재 경계가 적절한가?
- 주문·결제 상태 전이 버튼이 원우님 계약 확정 전 로컬 미리보기로만 표시된 현재 선이 적절한가?

### 10.3 기능 누락 여부

필수 기능 기준으로 빠진 것이 있는지 봐 달라.

현재 포함한 기능:

```text
1. 관리자 대시보드
2. 상품 조회/상태 확인
3. 단건 상품 등록/수정
4. 엑셀 기반 상품 대량 등록
5. 파일명 기반 이미지 대량 연결
6. OCR 후보 검수 보조
7. 성분 매핑 검수
8. 재고/가격 상태 확인 및 간단 수정
9. 주문/결제 상태 확인 및 로컬 운영 액션
10. API/job 연동 체크리스트
```

### 10.4 안전 규칙 정합성

아래 정책이 올바르게 유지됐는지 봐 달라.

- OCR 자동 확정 금지
- 성분은 내부 `ingredients.csv` canonical 기준
- 정규화 exact match만 자동 확정
- 부분일치 자동 확정 금지
- pending 성분은 검수 전 검색/추천 신호로 쓰지 않는 방향
- 이미지 단독 자동 상품 등록은 위험하므로 후보/검수 보조로 제한
- canonical 확정 주체를 세민님/데이터 계약으로 둔 표현이 충분히 명확한지
- `/admin` 권한 가드가 아직 미구현이며 API 연동 체크리스트에 필수 항목으로 들어간 것이 맞는지

### 10.5 UI/UX 검수

- 쇼핑몰 관리자 화면답게 보이는가?
- 너무 대시보드 카드가 많거나 정보가 과한가?
- 반대로 팀장님께 보여주기에는 아직 빈약한가?
- NHN 커머스/고도몰 관리자 참고 방향과 크게 어긋나지 않는가?
- 현재 디자인 토큰 사용이 프로젝트 톤과 맞는가?

### 10.6 커밋/PR 전략

이 변경은 이미 diff가 크다.

검토 요청:

- 지금 한 커밋으로 묶어도 되는가?
- 아니면 다음처럼 나누는 것이 맞는가?
  - 관리자 라우트/셸
  - 상품/엑셀/이미지
  - 성분 검수
  - 재고/주문

## 11. 현재 판단

Codex 현재 판단:

- 팀장님이 요구한 관리자 화면 필수 기능 6개는 로컬 화면 기준으로 대부분 완성됐다.
- 단건 상품 등록/수정까지 포함했으므로 운영 흐름은 더 자연스럽다.
- 실제 서비스 완성은 아니다. API 연결 전 화면 프로토타입이다.
- 지금 당장 PR보다 팀장님 중간 확인이 먼저다.
- 팀장님이 화면 방향을 OK하면 그 다음에 커밋/PR 단위를 나눠야 한다.

Claude에게 바라는 결론:

```text
1. 지금 팀장에게 보여도 되는 수준인지
2. 수정해야 할 큰 방향이 있는지
3. push/PR 전 커밋 단위를 어떻게 나눌지
4. 이 상태에서 더 만들지 말고 API 연결 논의로 넘어가야 하는지
```
