# 일반 상품 검색 v1 행동 명세

상태: API 계약 확정, 구현 진행
작성일: 2026-07-11
범위: 백엔드 일반 상품 검색. 피부 고민 맞춤 추천은 변경하지 않는다.

## 1. 목적

일반 상품 검색은 사용자가 이미 알고 있는 상품, 브랜드, 카테고리 또는 명시적인 상품 조건을 빠르게 찾는 기능이다.

```text
상품을 알고 있거나 조건을 직접 입력함 -> 일반 상품 검색
무엇을 골라야 할지 도움을 요청함       -> 피부 고민 맞춤 추천
```

일반 검색은 로그인 여부와 무관하게 같은 검색어에 같은 기본 결과를 반환한다. 저장 피부 프로필, 스킨 테스트, 사용자 행동 점수는 v1 일반 검색 랭킹에 사용하지 않는다.

## 2. 현재 카탈로그 스냅샷

`data/products/*.csv`를 2026-07-11에 직접 집계한 값이다. 문서에 남아 있는 과거 수치보다 현재 CSV를 우선한다.

| 항목 | 현재 값 |
| --- | ---: |
| 전체 상품 | 79,952 |
| `is_recommendable=true` | 10,164 |
| `is_recommendable=false` | 69,788 |
| 메이크업 | 28,310 |
| 헤어케어 | 14,068 |
| 바디케어 | 6,728 |
| 세럼 | 4,646 |
| 크림 | 4,328 |
| 세트 | 4,007 |
| 향수 | 1,625 |

`is_recommendable`은 피부 고민 맞춤 추천 후보 여부다. 일반 상품 검색은 이 값으로 상품을 제외하지 않는다.

## 3. 검색 대상

v1 검색 대상의 추천 기준은 다음과 같다.

- `Product.is_active=true`
- 연결된 브랜드와 카테고리가 활성 상태
- 재고 상태가 `HIDDEN`이 아님
- `SOLD_OUT`은 검색되지만 같은 관련도의 판매 가능 상품보다 뒤에 표시
- `is_recommendable=false`도 검색 가능
- 가격이나 이미지가 일부 없더라도 상품 식별 정보가 정상이면 검색 가능

상품 상세와 장바구니에서는 PostgreSQL의 최신 가격과 재고를 다시 검증한다. 검색 결과에 노출됐다는 사실만으로 구매 가능하다고 판단하지 않는다.

## 4. 검색어 처리 순서

```text
원문 보존
-> 공백/대소문자/기호 정규화
-> 브랜드·카테고리·성분·효능·가격 조건 인식
-> 정확 일치 검색
-> 일반 키워드 검색
-> 별칭·띄어쓰기 확장
-> 결과가 부족할 때만 제한적 오타 교정
-> 결과 또는 검색 복구 정보 반환
```

일반 검색은 추천용 `build_recommendation_intent()`와 분리한다. v1에서는 검색 요청마다 LLM 또는 embedding API를 호출하지 않는다.

## 5. 결과 순서 불변 조건

다음 조건은 이후 가중치를 조정하더라도 지켜야 한다.

1. 상품 코드 또는 상품명 정확 일치가 인기 상품보다 우선한다.
2. 사용자가 직접 지정한 브랜드, 카테고리, 가격, 평점, 재고 조건은 hard filter다.
3. 정확 일치 결과는 동의어·부분 일치·오타 결과보다 앞선다.
4. 인기, 평점, 리뷰 수, 신상품 여부는 관련도가 비슷한 상품 사이에서만 순서를 바꾼다.
5. `is_recommendable`은 일반 검색 점수와 노출 여부에 관여하지 않는다.
6. 검색 결과가 없을 때 무관한 인기 상품을 검색 결과인 것처럼 채우지 않는다.

초기 관련도 등급은 다음과 같이 정의한다.

| 등급 | 의미 |
| --- | --- |
| A | 상품 코드 또는 정규화된 상품명 정확 일치 |
| B | 브랜드와 상품명의 핵심 토큰 또는 구문 일치 |
| C | 카테고리, 성분, 효능, 피부 고민 일치 |
| D | 별칭, 부분 일치, 띄어쓰기 보정, 오타 교정 일치 |

## 6. 카테고리 해석

현재 CSV에는 같은 사용자 카테고리를 뜻하는 복수 코드가 있다. 기존 화면의 그룹을 기준으로 다음 묶음을 품질 케이스에 사용한다.

| 사용자 카테고리 | 허용 원본 코드 |
| --- | --- |
| 스킨케어 | `toner`, `serum`, `cream`, `lotion`, `set` |
| 클렌징 | `cleanser`, `cleansing`, `exfoliant` |
| 바디케어 | `bodycare`, `hair_body` |
| 헤어케어 | `haircare` |
| 뷰티소품 | `beauty_tool` |
| 마스크팩 | `mask`, `mask_pack` |
| 선케어 | `suncare`, `sunscreen` |
| 메이크업 | `makeup`, `eye_neck`, `spot` |
| 네일 | `nail` |
| 향수 | `fragrance` |

`men_allinone` 233건, `unknown` 25건, `accessory` 2건은 현재 화면 그룹에 없다. 검색 색인에서는 누락하지 않되 최종 facet 노출 그룹은 API 계약 단계에서 확정한다.

## 7. 검색 복구 정책

- 원 검색 결과와 교정 결과를 구분한다.
- 교정 검색어를 사용자가 확인할 수 있게 응답한다.
- 필터 때문에 결과가 없으면 제거할 수 있는 필터를 제안한다.
- 브랜드와 카테고리가 충돌하면 어느 조건을 완화할지 제안한다.
- 인기 상품은 별도 추천 영역으로만 표시할 수 있으며 검색 결과 수에는 포함하지 않는다.

## 8. 품질 케이스

기준 데이터는 `apps/backend/tests/catalog_search_quality_cases.json`에 둔다.

각 케이스는 다음 정보를 가질 수 있다.

- `type`: 정확 상품, 브랜드, 카테고리, 속성, 복합 조건, 오타/별칭, 결과 없음
- `query`: 사용자가 입력한 원문
- `expected.top_product_ids`: 상위에 있어야 하는 실제 상품 ID
- `expected.brand_names`: 허용 브랜드명
- `expected.category_codes`: 허용 원본 카테고리 코드
- `expected.required_terms`: 검색 문서 또는 상품 정보에서 확인할 핵심 용어
- `expected.filters`: 가격, 평점, 재고 등 hard filter
- `expected.correction`: 제안할 정규 검색어
- `expected.forbidden_product_ids`: 상위 결과에 나오면 안 되는 데이터 오염 상품

v1 구현 완료 기준은 다음과 같다.

| 품질 축 | 기준 |
| --- | --- |
| 정확 상품 | 정확 상품이 1위 |
| 브랜드 | 상위 10개 중 허용 브랜드 비율 90% 이상 |
| 카테고리 | 상위 20개 중 허용 카테고리 비율 90% 이상 |
| hard filter | 상위 결과 위반 0건 |
| 오타 교정 | 원문과 교정문을 구분하고 정확 결과보다 앞서지 않음 |
| 결과 없음 | 무관한 검색 결과 채우기 0건 |

이 수치는 검색 엔진 선택과 무관한 사용자 품질 기준이다. 실제 검색 결과 평가 테스트는 색인 v2가 구현된 뒤 같은 fixture를 읽어 추가한다.

## 9. 확인된 데이터 차단 이슈

검색 로직에서 숨기지 않고 원본 데이터 QA로 해결해야 한다.

| 문제 | 예시 |
| --- | --- |
| 해외 feed 브랜드 오염 | `cultbeauty_168b506cb8c907`은 브랜드가 `NARS`지만 상품명은 `Omorovicza` |
| 해외 feed 브랜드 오염 | `cultbeauty_374e38d075856c`은 브랜드가 `MAC`이지만 상품명은 `Manucurist` |
| 해외 feed 브랜드 오염 | `lookfantastic_c800073cfb9572`는 브랜드가 `MAC`이지만 상품명은 `VICHY` |
| 카테고리 중복 | `cleanser/cleansing`, `sunscreen/suncare`, `mask/mask_pack` |
| 화면 그룹 미정 | `men_allinone`, `unknown`, `accessory` |

브랜드 오염 상품은 품질 fixture에서 `catalog_data_blocked` 상태와 금지 상품으로 남긴다. 데이터가 정리되면 상태를 `ready`로 바꾸고 실제 검색 평가에 포함한다.

## 10. v1 비범위

- 저장 피부 프로필 기반 개인화
- 행동 데이터 기반 개인화 재정렬
- pgvector 또는 의미 검색
- 검색 요청당 LLM 호출
- 광고 상품 삽입
- 운영자용 검색 규칙 관리 화면
- 프론트엔드 화면 변경

## 11. 확정된 구현 결정

- `GET /api/search/products`, `GET /api/search/suggestions`를 신규 계약으로 사용한다.
- 페이지 번호와 `page_size`를 사용하고 기본 20, 최대 50으로 제한한다.
- 원본 카테고리 코드와 사용자용 통합 그룹을 함께 색인한다.
- `HIDDEN`은 제외하고 `SOLD_OUT`은 후순위로 노출한다.
- Nori 플러그인과 일반검색 전용 Elasticsearch alias를 사용한다.
- 띄어쓰기, 초성, 두벌식 자판 변환, 확정 alias, 제한 fuzzy 복구를 지원한다.

세부 request/response와 오류 계약은 `docs/catalog-search-api-contract.md`를 따른다.
