# 뭐바를래 최종 발표 PPT 최종 초안

작성일: 2026-07-10
상태: Final Draft — 측정값 입력 전
분류: **부록 A — 기술 리포트를 발표로 옮긴 예시 초안**
발표 시간: 7분
구성: 인트로 1분 · 시연 5분 · 클로징 1분

> 이 문서는 필수 기준이 아니다. 실제 발표 순서·문구·슬라이드는 팀 합의와 실측 결과에 따라 변경한다.

## 1. 발표가 남겨야 할 한 문장

> 뭐바를래는 LLM이 상품을 임의로 고르는 서비스가 아니라, 자연어 피부 고민을 구조화하고 성분·효능·함량·근거를 계산해 추천 순서를 설명하며, 실제 리뷰 경험으로 추천 적합성을 검증하는 뷰티 커머스다.

청중은 발표가 끝났을 때 다음 세 가지를 기억해야 한다.

1. 기존 성분 정보 서비스와 달리, 성분의 존재 여부를 넘어 함량과 효능 근거까지 추천 점수에 반영한다.
2. 리뷰에서 사용 전 고민을 복원해 입력했을 때 실제 긍정 경험 상품을 다시 찾는지 검증한다.
3. 추천 결과마다 `고민 → 효능 → 성분 → 함량 → 근거 → 상품` 경로를 보여주고, 이를 8만 상품에서도 실시간으로 계산한다.

현재 코드에는 인증 사용자의 유효한 행동 신호를 조건부로 반영하는 `v3_behavior_personalization`이 구현되어 있다. 행동 데이터가 없으면 해당 weight를 제외하고 기본 추천으로 fallback한다. 다만 효과는 ablation 전까지 검증 완료로 발표하지 않으며, Redis cache는 아직 실제 활성 경로로 확인되지 않는다.

## 4. 슬라이드별 구성

슬라이드는 12장이지만, 3~9번은 발표 자료를 길게 읽는 화면이 아니라 라이브 데모의 장면 전환 또는 장애 시 대체 화면으로 사용한다.

### 슬라이드 1. 성분표를 읽어주는 쇼핑몰에서, 근거로 추천하는 쇼핑몰로

화면 문구:

```text
성분표를 읽어주는 쇼핑몰에서,
근거로 추천하는 쇼핑몰로

뭐바를래
```

시각 요소:

- 화장품 전성분표 일부와 추천 카드 한 장을 대비
- 텍스트는 제목과 서비스명만 표시

발표자 메모:

> 화장품을 고를 때 우리는 성분표를 확인합니다. 하지만 어떤 성분이 들어 있다는 사실만으로는 그 성분이 내 고민에 왜 필요한지, 실제로 의미 있는 함량인지 알기 어렵습니다.

### 슬라이드 2. 같은 성분표도, 고민에 따라 추천 순서는 달라져야 합니다

화면 문구:

```text
기존 정보
성분이 들어 있다 · 주의 성분이다

뭐바를래
내 고민 → 필요한 효능 → 성분 → 함량 → 근거 → 상품 순위
```

하단 강조 문구:

> **LLM은 고민을 해석하고, 근거 기반 scoring engine이 순위를 결정합니다.**

시각 요소:

- 왼쪽: `성분 있음 / 주의`에서 멈추는 흐름
- 오른쪽: 고민에서 상품 순위까지 이어지는 한 줄 경로

발표자 메모:

> 저희가 공을 들인 부분은 단순한 AI 대화가 아닙니다. 자연어 고민을 표준 고민과 효능으로 바꾸고, 성분의 효능 점수, 근거 수준, 함량 구간과 피부 적합도를 계산해 상품 순위를 만듭니다. 지금부터 이 경로가 실제 화면에서 어떻게 드러나는지 보여드리겠습니다.

### 슬라이드 3. 오늘 해결할 고민

화면 문구:

```text
“속은 당기는데 겉은 기름지고,
자극 없이 진정되는 3만원 이하 세럼을 찾고 있어요.
알코올은 피하고 싶어요.”
```

시각 요소:

- 사용자 입력창을 크게 확대
- 데모 persona 이름은 사용하지 않고 고민 문장 자체에 집중

데모 동작:

1. 로그인 또는 준비된 세션 진입
2. 위 문장을 추천 입력창에 입력
3. 추천 요청 실행

### 슬라이드 4. 한 문장을 추천 가능한 조건으로 바꿉니다

화면 문구:

```text
고민        속건조 · 피지 · 민감
기대 효능   보습 장벽 · 진정 · 피지 케어
구매 조건   세럼 · 30,000원 이하
제외 조건   알코올
```

하단 강조 문구:

> 이해하지 못한 표현은 억지로 추천 근거에 넣지 않습니다.

데모 동작:

- 추천 summary의 `matched_concerns`, `expected_effects`, 가격/카테고리 조건 확인
- `unmatched_terms` 또는 검토가 필요한 입력 처리 방식 언급

기술 포인트:

- 규칙 parser가 명확한 조건을 추출
- LLM은 문맥, 동의어, 부정 표현을 보완
- LLM 결과를 그대로 상품 순위로 사용하지 않음

### 슬라이드 5. 상품 이름보다 먼저, 추천 이유를 보여줍니다

화면 문구:

```text
1위인 이유

진정 효능 성분 일치
유효 함량 구간 적합
근거 수준 높음
민감 피부 위험 감점 없음
```

데모 동작:

1. 추천 결과 상위 3개 확인
2. 1위 카드의 핵심 성분과 추천 이유 확인
3. 2위 제품과 무엇이 달라 순위가 갈렸는지 비교

발표자 메모:

> 같은 성분이 있어도 함량 구간과 근거 수준, 민감 피부 위험 여부가 다르면 점수가 달라집니다. 이 순위는 생성형 AI의 문장이 아니라 저장 가능한 score breakdown의 결과입니다.

### 슬라이드 6. 추천 점수를 다시 설명할 수 있어야 합니다

화면 문구:

```text
추천 점수

성분-효능       0.32
효능 근거       0.23
피부 적합도     0.14
함량 적합도     0.08
기능성 근거     0.05
검색 일치도     0.07
가격 적합도     0.04
+ 민감 피부 위험 감점
```

주의:

- 위 값은 현재 실제 ranking 계산에 사용되는 기본 scoring coefficient다.
- 실제 화면에 표시할 때는 `score_breakdown` 값과 일치시킨다.
- 검색 intent에 따라 조정된 weight를 사용한 경우 기본값과 조정값을 함께 표시한다.

데모 동작:

- 상품 상세 또는 추천 상세에서 score breakdown 확인
- 민감도, 위험 성분, 가격 조건이 순위에 반영된 부분 강조

### 슬라이드 7. 근거는 추천 문구가 아니라 추적 가능한 데이터입니다

화면 문구:

```text
고민
  ↓
진정 효능
  ↓
성분과 함량 구간
  ↓
논문 · DOI/PMID · 식약처 고시
```

하단 주석:

> 근거는 해당 성분과 효능의 연결을 설명하며, 제품 자체의 임상 효능을 보장하지 않습니다.

데모 동작:

1. 상위 상품의 핵심 성분 선택
2. 농도 bucket과 warning 확인
3. evidence level, 출처 유형, DOI/PMID 또는 고시 출처 확인

### 슬라이드 8. 같은 고민도 피부 타입과 민감도에 따라 순위가 달라집니다

화면 문구:

```text
현재 반영
건성/지성 · 민감도 · 최신 피부 테스트 · 유효한 사용자 행동 신호

결과
성분 근거를 중심에 두고 피부 맥락으로 순위를 조정

다음 검증
행동 축 ON/OFF ablation · 품질 개선 · latency 비용
```

데모 동작:

- 수동 피부 타입·민감도와 저장된 사용자 맥락 확인
- 동일 고민을 다른 피부 조건으로 실행
- 순위 또는 score breakdown에서 달라진 축 확인

발표자 메모:

> 성분과 근거가 추천의 중심이고, 피부 타입·민감도·피부 테스트와 유효한 행동 신호가 사용자 맥락에 맞게 순서를 조정합니다. 행동 데이터가 없으면 해당 축을 제외해 기본 추천으로 동작합니다. 구현 여부와 효과 검증을 구분하기 위해, 개선 수치는 행동 축을 끈 결과와 비교한 뒤 제시합니다.

### 슬라이드 9. 추천은 설명에서 끝나지 않고 구매 흐름으로 이어집니다

화면 문구:

```text
추천 → 상품 상세 → 장바구니 → 주문/결제 preview
```

데모 동작:

1. 추천 상품 상세 진입
2. 장바구니 추가
3. checkout preview 확인

발표자 메모:

> 추천 실험이 아니라 P2 자사몰의 실제 사용자 흐름 안에 추천을 연결했습니다. 추천 ID와 순위가 장바구니까지 이어져 이후 어떤 추천이 행동으로 전환됐는지도 추적할 수 있습니다.

### 슬라이드 10. 역할이 다른 저장소를 분리해 추천과 커머스를 함께 지켰습니다

화면 제목:

> **LLM은 언어를 이해하고, 검색 엔진은 후보를 줄이며, RDB는 근거와 거래를 지킵니다**

아키텍처 한 판:

```text
Vercel / React
      ↓
EC2 t3.large
Caddy → FastAPI
         ├─ Elasticsearch: 키워드 후보 검색
         ├─ Redis: cache 적용 준비
         └─ OpenAI: 고민 해석·서술 보조
      ↓
RDS PostgreSQL + pgvector
상품 · 성분 · 효능 · 함량 · 근거 · 사용자 · 주문 · vector 후보

S3 / CloudFront
상품 이미지
```

설명해야 할 이유:

- PostgreSQL: 추천 근거 데이터와 주문 transaction의 정합성
- pgvector: 자연어 의미가 비슷한 후보의 recall 확보
- Elasticsearch: 8만 상품에서 키워드·필터 기반 top-K 후보 축소
- Redis: 인프라와 설정은 준비되어 있으나 실제 cache 적용은 구현·검증 후 발표에 포함
- OpenAI: 비정형 고민 해석에 사용하되 최종 순위 결정권은 scoring engine에 유지
- S3/CloudFront: 이미지 전달을 API 서버에서 분리

### 슬라이드 11. 추천은 맞는가, 설명되는가, 빠른가로 검증합니다

화면 구성은 세 개의 숫자 축만 사용한다.

#### 축 1. 실제 리뷰의 긍정 상품을 다시 찾는가

```text
리뷰 고민 → 원래 긍정 상품 복원

HitRate@10
[측정 전] → 인기순/BM25 baseline 상회

MRR@10
[측정 전] → 측정 후 입력
```

#### 축 2. 왜 추천했는지 증명하고 제약을 지키는가

```text
Top-5 근거 경로 연결률
[측정 전] → 목표 95% 이상

함량 데이터 보유 상품의 함량 구간 판정 성공률
[측정 전] → 목표 99% 이상

제외 성분·가격 hard constraint 위반률
[측정 전] → 목표 0%
```

#### 축 3. 8만 상품 실시간 처리

```text
최초 문제 상태
홈 p95             60.00초
추천 생성 p95      52.17초
상품 검색 p95      32.29초
오류율             12.64%

목표
홈 p95              1.5초 이하
추천 core p95        3초 이하
상품 검색 p95        2초 이하
오류율               1% 미만
50 VU · 10분 안정 처리
```

하단 주석:

> 최초 수치는 2026-07-08 t3.xlarge, 상품 79,957건, 10 VU/4분 실패 실행의 문제 상태이며, 최종 개선 수치는 동일한 t3.large 환경에서 3회 재측정 후 입력합니다.

발표자 메모:

> 추천 품질은 별점 자체로 판단하지 않았습니다. 리뷰에서 사용 전 고민과 사용 후 긍정·부정 경험을 분리한 뒤, 고민만 다시 입력해 실제 긍정 경험 상품을 상위 10개 안에서 복원하는지 봅니다. 리뷰는 절대 정답이 아닌 silver label이고, 사람이 만든 gold set으로 보완합니다. 동시에 추천 이유의 근거 경로와 hard constraint를 확인하고, 8만 건에서는 동일 조건 세 번의 중앙값으로 응답 성능을 검증합니다.

### 슬라이드 12. 근거 데이터부터 구매까지, 각 역할이 하나의 추천을 완성했습니다

화면 구성:

- 팀원 사진 6장
- 사진 아래에는 이름보다 역할과 이번 발표에서 확인할 결과를 먼저 표시

```text
PM/UX
고민 입력부터 구매까지 사용자 흐름과 QA 기준
```

## 5. 발표용 KPI 체계

성능 수치만 제시하면 “느린 API를 빠르게 했다”는 이야기로 끝난다. 기술적 차별점을 증명하려면 추천 품질, 설명 가능성, 시스템 성능 세 축을 함께 제시한다.

### 5.1 추천 품질 KPI

추천 품질은 하나의 데이터셋으로 단정하지 않고 `review silver label → human gold set → online behavior`의 세 단계로 검증한다.

#### 5.1.1 리뷰 기반 silver-label 평가

리뷰가 연결된 상품을 유일한 정답으로 간주하지 않는다. 리뷰에서 특정 고민에 대한 긍정 또는 부정 경험을 추출해 `고민–상품 relevance`의 약한 정답으로 사용한다.

```text
원본 리뷰
→ 피부 타입·고민·효능별 문장 분리
→ 사용 전 고민과 사용 후 결과 분리
→ 효능별 긍정/부정 판정
→ 상품명·브랜드명·정답을 노출하는 표현 제거
→ 표준 고민·효능 tag 변환
→ relevance grade와 confidence 부여
→ 사람 표본 검수
→ 고정된 평가 데이터셋
```

권장 relevance grade:

| grade | 기준 |
| ---: | --- |
| 3 | 고민과 해당 효능의 구체적인 개선 또는 재구매 경험이 연결됨 |
| 2 | 피부 타입과 관련 효능의 긍정 경험이 명확함 |
| 1 | “촉촉하다”, “좋다”처럼 관련성은 있으나 근거가 약함 |
| 0 | 배송·향·용기 등 추천 효능과 무관함 |
| -1 | 해당 고민에서 악화·자극·부정 경험이 명확함 |

평가 데이터 최소 schema:

```text
review_id
product_id
concern_tags
effect_tags
skin_type
polarity
relevance_grade
label_confidence
leakage_flags
split
```

실제 데이터셋으로 만들 때는 리뷰 사용 권한을 확인하고 작성자 식별 정보와 원문에 포함된 개인정보를 제거한다. 이 schema를 CSV/JSON으로 확정할 때는 `docs/data-contract.md`도 함께 갱신한다.

레이블 품질 KPI:

| KPI | 발표 목표 |
| --- | ---: |
| Product mapping rate | 95% 이상 |
| Concern extraction precision | 90% 이상 |
| Effect sentiment precision | 90% 이상 |
| Leakage rate | 0% |
| Human agreement | Cohen's κ 0.70 이상 |
| Label coverage/grade 분포 | 측정값과 제외 사유 공개 |
| Eligibility mapping rate | 100% |

평가 KPI:

| KPI | 측정 방법 | 발표 기준 |
| --- | --- | --- |
| HitRate@10 | 개별 리뷰 고민에서 원래 긍정 상품이 Top-10에 등장한 비율 | 인기순·BM25 baseline 상회 |
| MRR@10 | 원래 긍정 상품이 얼마나 상위에 등장했는지 | baseline 상회, 측정값 제시 |
| Recall@50 | 추천 가능 상품 중 긍정 상품을 후보 추출 단계에서 놓치지 않은 비율 | 0.90 이상 |
| Concern-group NDCG@10 | 같은 표준 고민의 리뷰를 묶고 상품별 grade를 집계해 순위 평가 | 0.80 이상 |
| Negative exposure@10 | grade -1 상품이 같은 고민 Top-10에 노출되는 비율 | baseline 대비 감소 |

리뷰 평가의 유효성을 지키는 규칙:

- 별점이 아니라 고민·효능별 sentiment를 레이블로 사용한다.
- 상품명, 브랜드명, 상품 고유 문구를 입력에서 제거해 정답 누출을 막는다.
- 성분명이 정답 상품을 사실상 특정하면 입력에서 제거하거나 별도 leakage flag를 둔다.
- 인기 상품만 유리하지 않도록 review 수와 상품 popularity를 기준으로 head/mid/tail 결과를 따로 보고한다.
- 같은 리뷰의 중복·요약·파생 문장이 train과 test에 동시에 들어가지 않게 한다.
- 추천 parser와 동일한 LLM으로 review label을 만들 경우 오류가 서로 닮을 수 있으므로 사람이 표본을 검수한다.
- review label을 weight 조정에 사용한다면 시간 기준으로 train/dev/test를 분리하고 최종 test는 tuning에 사용하지 않는다.
- `is_recommendable = false`인 상품은 ranking 실패로 계산하지 않고 제외 사유별로 별도 집계한다.

#### 5.1.2 사람이 만든 gold-set 평가

리뷰는 이미 구매하고 노출된 상품에 편향되어 있으므로, PM/도메인 검토자가 만든 독립적인 gold set으로 보완한다.

| KPI | 측정 방법 | 발표 목표 |
| --- | --- | ---: |
| Concern extraction F1 | 대표 고민 문장에서 표준 고민 tag 비교 | 0.90 이상 |
| Effect extraction F1 | 기대 효능과 parser 결과 비교 | 0.90 이상 |
| Purchase constraint accuracy | 카테고리·브랜드·가격 추출 정확도 | 95% 이상 |
| Hard constraint violation | 제외 성분·가격·카테고리 위반 상품 비율 | 0% |
| Expert relevance NDCG@10 | 검토자가 부여한 상품 relevance grade로 평가 | 0.80 이상 |

권장 gold set:

- 자연어 고민 100~200문장
- 명확한 표현, 동의어, 복합 고민, 부정 표현, 위험 표현 포함
- 피부 타입, 민감도, 가격, 제외 성분 조합 포함
- 최소 2명이 독립적으로 annotation하고 불일치 항목을 합의

#### 5.1.3 실제 서비스 행동 평가

리뷰 replay와 gold set은 offline 평가다. 서비스 오픈 후에는 추천이 실제 행동으로 이어지는지 별도로 확인한다.

| KPI | 의미 |
| --- | --- |
| 추천 노출 대비 클릭률 | 추천 결과가 관심을 만들었는지 |
| 클릭 대비 장바구니 전환율 | 추천 이유가 구매 고려로 이어졌는지 |
| 장바구니 대비 구매 전환율 | 추천이 실제 구매로 이어졌는지 |
| 추천 후 부정 행동률 | 찜/장바구니 제거와 부정 피드백이 증가하지 않는지 |

#### 5.1.4 차별점을 증명하는 ablation test

최종 알고리즘 점수만 제시하지 않고 동일한 review/gold test에서 추천 축을 단계적으로 추가해 비교한다.

```text
인기순
→ BM25/keyword
→ 성분 포함 여부
→ 성분 + 효능
→ 성분 + 효능 + 근거
→ 성분 + 효능 + 근거 + 함량
→ 전체 scoring
```

각 단계에서 HitRate@10, MRR@10, NDCG@10, hard constraint violation을 비교한다. 특히 근거 축과 함량 축을 제거했을 때 품질이 얼마나 하락하는지가 뭐바를래의 기술적 차별점을 직접 설명한다.

### 5.2 설명 가능성 KPI

| KPI | 측정 방법 | 발표 목표 |
| --- | --- | ---: |
| Score breakdown 제공률 | Top-5 결과 중 모든 score 축이 저장된 비율 | 100% |
| Evidence path coverage | Top-5 중 고민→효능→성분→근거 경로가 1개 이상인 비율 | 95% 이상 |
| Source traceability | 근거에 source type과 URL/DOI/PMID가 있는 비율 | 95% 이상 |
| Concentration decision success | 함량 데이터가 있는 대상의 bucket 판정 성공률 | 99% 이상 |
| Explanation consistency | 표시 이유와 실제 상위 기여 score 축이 일치하는 비율 | 95% 이상 |

함량 데이터 자체가 공개되지 않은 상품은 실패로 숨기지 않는다. 전체 상품 중 함량 데이터 coverage와, 함량 데이터가 존재할 때 판정에 성공한 비율을 분리해서 발표한다.

## 6. 기술적 챌린지의 서사

### 챌린지 1. 자연어 고민을 구조화하고 정답 없는 추천을 평가 가능하게 만들기

문제:

- 사용자는 “속은 당기고 겉은 기름져요”처럼 비정형 문장을 사용한다.
- 단순 keyword match는 동의어, 부정, 우선순위, 복합 고민을 놓친다.
- 추천에는 하나의 정답 상품이 없어서 일반적인 정확도로 품질을 설명하기 어렵다.
- 리뷰는 실제 경험이지만 구매·노출·인기 상품에 편향되어 있다.

접근:

- 규칙 parser로 명확한 조건을 안정적으로 추출
- LLM으로 문맥과 의미를 보완
- 결과를 표준 고민·효능·구매 조건 schema로 제한
- 위험하거나 모호한 표현은 `unmatched_terms`와 review 대상으로 보존
- 리뷰에서 사용 전 고민과 사용 후 긍정·부정 경험을 분리해 silver label 생성
- 상품명·브랜드명 등 정답 누출을 제거하고 relevance grade와 confidence 저장
- review test를 고정하고 사람이 만든 gold set으로 편향을 보완

증명 KPI:

- Concern/Effect extraction F1
- constraint accuracy
- review HitRate@10과 MRR@10
- concern-group NDCG@10
- negative exposure@10

### 챌린지 2. 논문과 함량을 상품 순위로 바꾸되 설명 가능하게 유지하기

문제:

- 성분이 포함됐다는 사실만으로 유효성을 판단할 수 없다.
- 논문 근거와 식약처 고시는 형태와 신뢰 수준이 다르다.
- 피부 맥락과 행동 개인화 신호가 강해지면 추천 이유가 불투명해질 수 있다.

접근:

- 성분-효능 점수와 evidence score 분리
- 함량을 meaningful/optimal/excessive 등의 구간으로 평가
- 피부 타입·민감도·위험 성분 penalty 반영
- 피부 타입·민감도·피부 테스트와 조건부 행동 개인화를 score 축으로 저장
- 행동 데이터가 없으면 행동 weight를 0으로 만들고 나머지 축을 재정규화
- 행동 축 ON/OFF ablation으로 품질과 latency 효과 검증
- 최종 결과에 scoring version, 적용 weight profile, evidence를 함께 보존

증명 KPI:

- Evidence path coverage
- concentration decision success
- explanation consistency
- NDCG@10과 hard constraint violation
- 근거·함량 축 제거 전후의 ablation 성능 차이

### 챌린지 3. 8만 상품에서도 실시간 추천하기

문제:

- 최초 구현은 최종 10개를 반환하기 위해 상품 약 7.9만 건과 성분 수십만 행을 읽었다.
- 홈 p95 60초, 추천 p95 52.17초, 검색 p95 32.29초까지 증가했다.
- Elasticsearch가 거의 사용되지 않고 PostgreSQL fallback에 부하가 몰렸다.

접근:

- Elasticsearch keyword와 pgvector semantic retrieval로 top-K 후보 축소
- 후보 ID를 먼저 제한하고 필요한 상품만 hydrate
- 검색 coverage count 최적화와 반복 결과 cache 도입 검토
- 추천 pipeline을 intent/candidate/match/scoring/save 단계로 분해해 병목 측정
- VU 기반 사용자 여정과 arrival-rate 기반 endpoint 한계 테스트를 분리

증명 KPI:

- API p95/p99
- 최대 지속 req/s와 처리량 유지율
- ES/pgvector 성공률과 DB fallback 비율
- DB row 수, slow query/request, RDS CPU

## 7. 데모 실패 대비 자료

라이브 데모가 실패해도 발표 흐름이 끊기지 않도록 다음 화면을 미리 준비한다.

1. 고민 입력부터 추천 결과까지 45초 녹화 영상
2. 추천 summary 스크린샷
3. 1위와 2위 score breakdown 비교 화면
4. 함량 bucket과 근거 출처 화면
5. 장바구니와 checkout preview 화면
6. 정상 실행의 recommendation ID와 고정 상품 ID

데모 환경에서는 다음을 고정한다.

- 사전에 검증한 고민 문장 1개
- 상품·검색 index와 alias
- 로그인 세션과 피부 프로필
- LLM timeout 시 fallback 결과
- 추천 결과가 존재하는 대표 상품
- CloudFront 이미지 정상 여부
