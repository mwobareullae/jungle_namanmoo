# 관리자 페이지 배치 설계도 (Layout Blueprint)

작성일: 2026-07-07  
기준 브랜치: `feat/admin-dashboard-shell`  
대상: 관리자 페이지 `/admin`  
성격: 디자인·구현·API보다 앞서는 배치 기준 문서. "어떻게 예쁘게 보일지"보다 **무엇이 어디에 있어야 하는지**를 먼저 고정한다.

근거:

- 팀장 공유 문서: 관리자 페이지 구현 순서 정리
- `docs/admin-dashboard-team-lead-comparison.md`
- 2026-07-07 로컬 `/admin` 실측: 현재 5173 기준 시안
- NHN Commerce shop by 상품 관리, 고도몰 관리자 화면 관례

## 0. 읽는 법

- 팀장: 각 화면의 구성·컬럼·흐름이 의도와 맞는지 확인한다. 열린 결정은 14절 6건이다.
- 원우: 각 화면의 API 필요 지점과 12절 총괄표를 확인한다. 경로는 전부 가칭이며 계약 정본은 원우 API 문서다.
- 지운: 이미지 저장소, import 후 검색 문서 rebuild, 임베딩 자동 반영, 관리자 권한/운영 로그 연결을 확인한다.
- 세민: 성분 canonical 기준, 성분 매핑 검수 절차, 이미지 파일명 규칙과 기존 데이터 정합성을 확인한다.
- 디자인/클로드: 현재 5173 기준 시안의 톤과 밀도는 살리되, 이 문서의 배치와 업무 흐름을 바꾸지 않는다.

표기 규칙:

- **(기존)** 현재 `/admin` 프로토타입에 이미 있음
- **(신규)** 이번 설계에서 추가해야 함
- **(예정)** 자리만 잡고 API/데이터 계약 후 연결
- **(준비중)** 화면에 비활성으로 노출

## 1. 전역 원칙

1. 상품·이미지·엑셀·재고·주문은 전부 `seller_id` 기준으로 본다. `product_code` 단독, `sku_code` 단독으로 찾지 않는다.
2. 초기 운영 범위는 본사 셀러 1개 고정이다. 모든 화면에는 현재 운영 범위를 표시하고, 셀러 선택 UI는 read-only로 자리만 둔다.
3. 상태값 어휘는 전 화면 공통 enum을 쓴다. 화면마다 다른 말을 만들지 않는다.
4. 자동 확정 안전 규칙은 유지한다: OCR 자동 확정 금지, 이미지 단독 자동 상품 생성 금지, 성분은 내부 `ingredients.csv` canonical 기준 정규화 exact match만 자동 확정, 부분일치 자동 확정 금지, pending 성분은 검수 전 검색/추천 신호로 사용 금지.
5. 성분 canonical 확정 주체는 세민/데이터 계약 절차다. 화면은 검수 도구이지 성분 기준을 임의로 확정하는 주체가 아니다.
6. 모든 쓰기 동작(등록·수정·검수·재고 변경·업로드)은 작업 로그에 `seller_id`와 함께 남긴다.

### 1.1 상품 상태 표준 enum

팀장 문서 5절 기준 화면 표기는 아래 8종을 정본으로 둔다.

```text
임시저장 / 등록완료 / 검수대기 / 판매가능 / 판매중 / 판매중지 / 품절 / 오류
```

어휘 교정:

- "검수필요"는 **검수대기**로 통일한다.
- "판매가능"과 "판매중"은 서로 다른 상태로 존치한다.
- "품절임박"은 상품 상태가 아니라 **재고 부족 필터**로 이동한다.
- 새 재고 상태값을 만들지 않는다.
- 화면 표기는 팀장 표준 enum을 고정 기준으로 삼고, 내부 코드값만 원우 API 계약에 맞춘다.

이미지 상태·성분 상태·인덱스 상태는 상품 상태와 섞지 않고 별도 보조 축으로 병기한다.

## 2. 공통 셸

### 2.1 좌측 메뉴

현재 5173 화면의 네이비 사이드바 톤은 유지하되, flat 8개 메뉴를 업무 그룹으로 묶는다.

```text
대시보드

상품 운영
  - 상품 조회/상태 확인
  - 상품 등록/수정
  - 엑셀 상품 대량 등록
  - 이미지 대량 연결
  - 성분 매핑 검수
  - 재고/가격 확인

주문 운영
  - 주문 상태 확인

셀러 운영 (준비중)
  - 셀러 관리
  - 셀러별 상품 검수
  - 셀러별 정산

운영 설정 (준비중)
  - 카테고리·브랜드 관리
  - 성분 사전 관리
  - 이미지 파일명 규칙
  - 엑셀 업로드 양식
  - 관리자 권한/작업 로그
```

`셀러 운영`, `운영 설정`은 초기에는 준비중 표시로 둔다. 숨기지 않는다. 나중에 확장될 관리자 구조를 팀장이 볼 수 있어야 한다.

### 2.2 상단 헤더

모든 화면 상단에는 같은 운영 범위 표시가 필요하다.

```text
현재 운영 범위: 본사 셀러
권한: 플랫폼 상품 운영자
기준일: 2026-07-07
```

초기에는 본사 셀러 1개 고정으로 충분하다. 다만 화면과 API 설계는 처음부터 `seller_id` 기준으로 둔다.

### 2.3 화면 공통 골격

각 화면은 아래 구조를 기본으로 한다.

```text
화면 제목
설명/주의 문구
운영 범위 표시
필터 영역
주요 작업 버튼
목록/테이블
선택 항목 상세 또는 결과 패널
API/운영 연결 필요 항목
```

## 3. 대시보드

목적: 운영자가 오늘 무엇을 처리해야 하는지 보는 화면.

### 3.1 상단 지표 카드

현재 화면의 카드 밀도는 유지하고, 지표는 아래 8종으로 정리한다.

```text
전체 상품
추천 가능
판매중
검수 대기
재고 부족
이미지 누락
전성분 원문 보유
인덱스 대기
```

주의:

- "재고 부족"은 상태 enum이 아니라 재고 필터 기준이다.
- "전성분 원문 보유" 카드는 성분 파이프라인 핵심 지표라 유지한다.
- 카드 클릭 시 해당 화면으로 이동하며 같은 필터가 걸린 상태로 열린다.

### 3.2 본문 배치

```text
처리 대기 큐
- 성분 매핑 검수 대기
- 상품명 중복 후보
- 엑셀 import 실패 행
- 이미지 매칭 실패
- 인덱스/임베딩 반영 대기

셀러별 이슈 요약
- 초기: 본사 셀러 1행
- 컬럼: 검수 대기 / 이미지 누락 / 재고 부족 / 인덱스 대기

최근 작업 로그
- 엑셀 업로드
- 이미지 매칭
- 성분 검수
- 검색 문서 rebuild

인덱스 상태
- 검색 문서 반영
- 임베딩 반영
- 마지막 rebuild 시각
```

`필수 6개 화면 체크` 카드가 현재 프로토타입에 있다면 구조 확인용으로 유지하되, 실제 운영 화면에서는 제거 후보로 둔다.

### 3.3 API 필요

- `GET /admin/dashboard` (가칭)
- 필요값: `seller_id`, 지표 집계, 처리 대기 카운트, 최근 작업 로그, 인덱스 상태

## 4. 상품 조회/상태 확인

목적: 관리자 화면의 중심. 모든 작업은 상품 조회에서 출발해 상세/수정/이미지/성분/재고/인덱스로 이어진다.

### 4.1 상단 필터

```text
셀러 범위: 본사 셀러 (read-only)
검색어: 상품명 / product_code / 브랜드
상품 상태: 전체 / 임시저장 / 등록완료 / 검수대기 / 판매가능 / 판매중 / 판매중지 / 품절 / 오류
카테고리
브랜드
전시 상태: 전체 / 노출 / 숨김
성분 상태: 전체 / 정상 / 검수대기 / pending 포함
이미지 상태: 전체 / 정상 / 이미지대기 / 매칭실패
인덱스 상태: 전체 / 반영완료 / 인덱스대기 / 임베딩대기
재고 필터: 전체 / 재고 부족 / 품절
등록일/수정일 기간
```

주의:

- 상품 상태와 판매 상태를 별도 축으로 나누지 않는다. 팀장 표준 enum 한 축으로 통합한다.
- 성분명 검색은 유용하지만 API 범위 확장이다. 14절 열린 결정에서 원우 확인을 받는다.

### 4.2 목록 컬럼

기본 노출:

```text
썸네일
상품명
브랜드
product_code
셀러
카테고리
가격/재고
상품 상태
전시 상태
성분 상태
이미지 상태
인덱스 상태
최근 수정일
관리
```

컬럼 토글 또는 상세 노출:

```text

담당자
업로드 회차(import job 번호 링크)
등록일
전성분 원문 보유 여부
```

### 4.3 관리 버튼

```text
상세/수정
이미지 연결
성분 검수
재고/가격 보기
인덱스 재반영 요청
```

### 4.4 API 필요

- `GET /admin/products` (가칭)
- `GET /admin/products/{product_id}` (가칭)
- `PATCH /admin/products/{product_id}` (가칭)

필수 조건:

- `seller_id` 필터

- `image_status`, `ingredient_status`, `index_status` 포함
- 업로드 회차(import job 번호) 연결

## 5. 상품 등록/수정

목적: 엑셀 없이 한 건을 바로 등록하거나 보정하는 화면. 팀장 6개 화면 외 추가 후보로 공유된 기능이다.

### 5.1 필드

```text
seller_id (본사 셀러 고정 표시)
product_code
상품명
브랜드
카테고리
상품 상태
전시 상태
가격 요약
재고 요약
전성분 원문
상품 이미지
검색/추천 노출 여부
```

### 5.2 저장 원칙

- `product_code`만으로 저장하지 않는다.
- `seller_id + product_code` 기준으로 저장한다.
- 성분은 자동 확정하지 않는다.
- 내부 `ingredients.csv` 기준 정규화 exact match만 자동 확정한다.
- 나머지는 pending 검수로 보낸다.
- 저장 시 작업 로그를 남긴다.

### 5.3 API 필요

- `GET /admin/products/{product_id}` (가칭)
- `PUT /admin/products/{product_id}` (가칭)

## 6. 엑셀 상품 대량 등록

목적: 검증 없이 DB에 들어가는 일이 없도록, 업로드 흐름을 단계로 보이게 한다.

### 6.1 화면 흐름

```text
1. 템플릿 다운로드
2. 업로드 대상 셀러 확인
3. 엑셀 파일 업로드
4. 컬럼/필수값 검증
5. 정상 행 / 오류 행 미리보기
6. 등록 실행
7. 성공/실패 리포트
8. 실패 row 다운로드
9. 검색 문서 rebuild / 임베딩 반영 대기열 생성
```

### 6.2 검증 항목

```text
필수 컬럼 누락
seller_id 누락
product_code 누락
같은 seller_id 안의 product_code 중복
기존 카탈로그 상품명 중복 후보
브랜드/카테고리 누락
가격/재고 숫자 오류
전성분 원문 누락
이미지 파일명 참조 오류
```

### 6.3 부분 성공 정책

- 성공 행은 커밋한다.
- 실패 행은 실패 결과 파일로 제공한다.
- 전체 rollback, 실패 row 재시도 UI는 확장 단계로 둔다.

### 6.4 API 필요

- `POST /admin/import-jobs` (가칭)
- `GET /admin/import-jobs` (가칭)
- `GET /admin/import-jobs/{id}/failures` (가칭)

확인:

- 검증/실행 분리
- 실패 row 저장·조회
- 업로드 회차 = import job 번호로 정의할지
- import 후 검색 문서 rebuild와 임베딩 자동 반영 방식

## 7. 이미지 대량 연결

목적: 파일명 규칙으로 이미지를 상품에 대량 연결하되, 상품 생성은 하지 않는다.

### 7.1 상단 안내

```text
대상 셀러: 본사 셀러
이미지 매칭 기준: seller_id + product_code
```

금지 문구:

- `product_code`만으로 상품을 찾지 않는다.
- 이미지 파일만으로 상품을 자동 생성하지 않는다.
- OCR 결과만으로 성분을 자동 확정하지 않는다.

### 7.2 본문 배치

```text
파일 업로드
파일명 규칙 안내
매칭 완료 목록
미매칭 목록
중복 후보 목록
실패 파일 다운로드
대표 이미지 확정
```

### 7.3 API 필요

- 이미지 업로드 저장소 — 지운 확인
- `POST /admin/images` (가칭)
- `POST /admin/images/match` (가칭)

확인:

- 실제 기존 이미지 파일명과 새 파일명 규칙의 정합성
- `seller_id + product_code` 기준 매칭
- 파일명 규칙 관리 화면이 운영 설정에 필요한지

## 8. 성분 매핑 검수

목적: pending 성분을 사람 눈으로 canonical에 연결하거나 보류/반려하는 화면.

### 8.1 배치

좌측:

```text
pending 성분 후보 목록
발생 상품 수
우선순위
자동 후보 여부
검수 상태
```

우측:

```text
선택 성분 원문
상품별 전성분 원문
정규화 exact match 후보
내부 ingredients.csv canonical 후보
승인 / 보류 / 반려
reason 입력
검수 이력
```

### 8.2 안전 규칙

- 국문/영문 표준명 정규화 exact match만 자동 확정 후보로 보여준다.
- 부분일치는 자동 확정하지 않는다.
- accepted alias가 쌓이기 전에는 대부분 pending 검수로 흐른다.
- OCR은 후보 추출 보조만 가능하다.

### 8.3 API 필요

- `GET /admin/ingredient-reviews` (가칭)
- `POST /admin/ingredient-reviews` (가칭)

필수:

- pending 목록
- 승인/보류/반려 + reason
- 검수 이력
- canonical 반영 절차는 세민/데이터 계약 기준

## 13. 디자인 적용 지점

디자인은 이 문서의 배치를 바꾸지 않는다. 현재 5173 기준 시안의 밀도와 톤을 유지하고, 아래 지점만 화면 구조에 맞게 마감한다.

```text
셸
- 사이드바 그룹 라벨
- 준비중 표시
- 헤더의 운영 범위/권한 칩

대시보드
- 지표 카드 8종
- 셀러별 이슈 요약
- 처리 대기 큐

상품 목록
- 필터 바
- 컬럼 토글
- 상태/보조 상태 배지

엑셀
- 5단계 스텝퍼
- 성공/실패 리포트

이미지
- 매칭 완료/미매칭/중복/누락 탭

성분
- 좌측 pending 목록
- 우측 원문/후보/검수 패널
```

배지 매핑은 상품 상태 enum 8종과 보조 축(이미지/성분/인덱스)을 분리해서 만든다. 상품 상태와 보조 상태를 같은 enum처럼 섞지 않는다.

## 14. 확정 필요 (열린 결정 6건)

1. **단건 상품 등록/수정 포함 확정** — 팀장 6개 화면 외 추가 후보. 엑셀 없이 한 건을 바로 보정하는 기능으로 포함 권고.
2. **전시상태 필드 존재/도입 시점** — 현재 데이터에 없다면 기본값과 도입 시점을 세민·원우가 확인해야 한다.
3. **담당자 mock 허용** — 권한 API 전까지 담당자를 mock으로 노출해도 되는지 확인이 필요하다.
4. **업로드 회차 = import job 번호 정의** — 목록 컬럼과 실패 리포트 링크 기준을 import job 번호로 둘지 확인한다.
5. **이미지 파일명 규칙** — 기존 실파일명과 새 규칙의 정합성을 지운·세민이 확인한다. 기준은 `seller_id + product_code`이며 `product_code` 단독 매칭은 금지한다.
6. **상품의 성분명 검색 포함 여부** — 상품 조회 검색어에 성분명을 포함할지 원우 API 범위 확인이 필요하다.
