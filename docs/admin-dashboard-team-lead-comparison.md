# 관리자 페이지 팀장 구현 순서 대비 현황 정리

작성일: 2026-07-07  
브랜치: `feat/admin-dashboard-shell`  
기준 자료: 팀장 공유 문서 `관리자 페이지 구현 순서 정리` + 현재 `/admin` 로컬 프로토타입

## 1. 결론

현재 `/admin` 프로토타입은 팀장님이 말한 필수 운영 화면의 큰 흐름은 대부분 갖추고 있다.

- 관리자 대시보드
- 상품 조회/상태 확인
- 단건 상품 등록/수정
- 엑셀 기반 상품 대량 등록
- 파일명 기반 이미지 대량 연결
- OCR 후보 추출 보조
- 성분 매핑 검수
- 재고/가격 상태 확인
- 주문/결제 상태 확인
- API/job 연동 체크리스트

다만 팀장님 문서의 핵심은 화면 개수보다 `seller_id` 중심 운영 구조다. 현재 프로토타입은 화면 흐름과 mock 동작은 많이 만들어졌지만, 아래 구조는 아직 약하다.

- 현재 운영 범위 표시: `본사 셀러`, `전체 셀러`, 특정 셀러
- 플랫폼 관리자와 셀러 관리자 권한 구분
- 상품/이미지/엑셀/재고/주문을 `seller_id + product_code` 또는 `seller_id + sku_code`로 다루는 기준
- 작업 로그와 변경 이력의 `seller_id` 귀속
- SKU/옵션 단위 재고/가격
- 주문 품목별 셀러 귀속

따라서 다음 작업의 중심은 화면에 `셀러 범위`, `권한`, `SKU`, `작업 로그`, `seller_id 기준`을 드러내는 것이다. 디자인 교체는 이 구조 확인 후 그 위에 입힌다.

## 2. 팀장 지시의 핵심 해석

팀장님 문서는 일반 쇼핑몰 전체 관리자보다, 상품 데이터를 빠르게 등록하고 운영 가능한 상태로 검수하는 관리자에 초점을 둔다.

핵심 흐름:

```text
셀러 선택 또는 기본 셀러 적용
-> 상품 데이터 준비
-> 엑셀 기반 상품 대량 등록
-> 이미지 대량 연결
-> 성분 매핑 검수
-> 재고/가격 상태 확인
-> 주문 상태 확인
```

초기에는 본사 셀러 1개만 써도 되지만, 데이터와 API는 나중에 다중 셀러로 확장될 수 있어야 한다.

중요 원칙:

- 화면은 단순하게 시작해도 된다.
- 내부 데이터와 API는 `seller_id` 기준을 가져야 한다.
- `product_code`만으로 상품을 찾으면 안 된다.
- `sku_code`만으로 재고/가격을 찾으면 안 된다.
- 이미지 매칭도 `seller_id + product_code` 기준이어야 한다.
- 플랫폼 공통 데이터와 셀러별 데이터를 분리해야 한다.

## 3. 현재 구현과 팀장 Step 비교

| 팀장 Step | 요구 내용 | 현재 `/admin` 구현 | 판정 | 남은 일 |
|---|---|---|---|---|
| Step 1 관리자 기본 레이아웃 | 사이드바, 헤더, 접근 범위, 메뉴 그룹, 공통 UI | 사이드바/메뉴/화면 구조 있음. 헤더와 공통 카드/테이블 UI 있음 | 부분 완료 | 현재 운영 범위 `본사 셀러` 표시, 로그인 사용자/권한 표시, 메뉴 그룹화 필요 |
| Step 2 셀러 모델/권한 기반 | 기본 셀러, `seller_id`, 관리자 역할, API 범위 제한 | API 연동 체크리스트에 관리자 접근 제어만 있음 | 미완료 | 백엔드 모델/API 영역. 화면에는 셀러 범위와 역할 표시 필요 |
| Step 3 대시보드 | 처리 대기, 최근 작업, 셀러별 이슈 요약 | 지표, 처리 대기, import job, 로그, 인덱스 상태 있음 | 부분 완료 | 셀러별 이슈 요약, 권한별 집계 범위, 카드 클릭의 셀러 필터 연동 필요 |
| Step 4 상품 조회/상태 확인 | 검색, 상태 필터, 셀러 필터, SKU, 썸네일, 담당자 | 상품 검색/상태 필터/상태 컬럼 있음 | 부분 완료 | 셀러 필터, SKU 컬럼, 썸네일, 카테고리, 전시상태, 등록일/수정일, 업로드 회차, 담당자 필요 |
| Step 5 엑셀 대량 등록 | 양식, 업로드, 검증, 미리보기, 등록 실행, 실패 리포트 | 템플릿/검증/실패 파일/대기열 mock 있음 | 부분 완료 | 업로드 셀러 지정, 등록 전 미리보기, 실제 파싱, 같은 셀러 내 중복 검증, 작업 로그 필요 |
| Step 6 이미지 대량 연결 | ZIP/다중 업로드, 파일명 규칙, `seller_id + product_code` 매칭 | 파일 선택, 규칙, 매칭 결과, 실패 파일 mock 있음 | 부분 완료 | `seller_id + product_code` 기준을 화면에 더 명확히 표시, ZIP/다중 업로드 실제 연결 필요 |
| Step 7 성분 매핑 검수 | 원문, 자동 매핑, 승인/수정/보류, 사전 검색, 이력 | pending 후보, 승인/보류/반려, 후보 CSV 있음 | 부분 완료 | 상품별 원문 확인, 성분 사전 검색, 신규 성분 요청, 검수 이력, 셀러 상품 귀속 표시 필요 |
| Step 8 재고/가격 확인 | SKU/옵션별 재고, 가격, 셀러 필터, 이력 | 상품 단위 재고/가격 수정 mock, 이력 CSV 있음 | 부분 완료 | SKU/옵션 단위로 바꾸기, 셀러 필터, 가격 이상/누락 필터 필요 |
| Step 9 주문 상태 확인 | 주문/결제/배송/취소/환불/반품 상태, 주문 품목별 셀러 | 주문/결제 목록과 로컬 상태 전이 있음 | 부분 완료 | 팀장 기준은 우선 조회 중심. 주문 품목별 seller_id, 배송/환불/반품 상태 표시 필요 |
| Step 10 작업 로그/변경 이력 | 업로드, 이미지, 성분, 상품, 재고, 관리자별 이력 | 운영 로그와 일부 CSV 이력 있음 | 부분 완료 | 독립 작업 로그 화면, 관리자별/셀러별 로그, 실제 API 로그 필요 |
| Step 11 관리자 권한 관리 | 계정, 역할, 메뉴 권한, 작업 권한 | 체크리스트에만 있음 | 미완료 | 화면 또는 최소 권한 표시/읽기 전용 상태 필요. 실제 권한 API는 원우 영역 |

## 4. 현재 구현에서 이미 살릴 수 있는 것

새 디자인을 클로드가 다시 뽑더라도 아래 기능 흐름은 유지할 가치가 있다.

### 유지할 기능 흐름

- 대시보드의 처리 대기 카드
- 상품 조회에서 행 클릭 시 단건 수정으로 이동
- 단건 상품 등록/수정의 전성분 exact/pending 미리보기
- 엑셀 업로드의 템플릿 다운로드, 검증, 실패 파일 다운로드
- 이미지 업로드의 파일명 규칙, 매칭 결과, 실패 파일 다운로드
- OCR은 자동 등록이 아니라 후보 추출/검수 보조로 제한
- 성분 검수의 승인/보류/반려 상태 변경
- 재고/가격 변경 이력
- 주문 상태 조회와 원우 확인 필요 상태 전이
- API/job 연동 체크리스트 CSV

### 유지할 안전 규칙

- OCR 자동 확정 금지
- 이미지 단독 자동 상품 생성 금지
- 성분은 내부 `ingredients.csv` canonical 기준
- 정규화 exact match만 자동 확정
- 부분일치 자동 확정 금지
- pending 성분은 검수 전 검색/추천 신호로 사용하지 않음
- 성분 canonical 확정 주체는 세민님/데이터 계약
- 주문/결제 상태 전이는 원우님 API 계약 확인 전에는 mock 미리보기

## 5. 현재 구현에서 반드시 보강해야 할 것

### 5.1 셀러 컨텍스트

현재 화면에는 `seller_sku` 같은 표현은 있지만, 관리자 전체 구조가 `seller_id` 중심으로 보이지 않는다.

보강안:

- 상단 헤더에 현재 범위 표시

```text
현재 운영 범위: 본사 셀러
권한: 플랫폼 상품 운영자
```

- 상품/엑셀/이미지/재고/주문 화면 필터에 셀러 필터 자리 추가
- 초기에는 read-only 셀러 선택처럼 보여도 됨
- 문구는 "현재는 본사 셀러 고정, 추후 플랫폼 관리자만 셀러 선택"으로 표시

### 5.2 메뉴 그룹

현재 메뉴는 flat 구조다. 팀장님 문서처럼 운영 영역별 그룹으로 나누는 편이 좋다.

권장 구조:

```text
대시보드

상품 운영
- 상품 조회/상태 확인
- 상품 등록/수정
- 엑셀 상품 대량 등록
- 이미지 대량 연결
- 성분 매핑 검수
- 재고/가격 확인

주문 운영
- 주문 상태 확인

셀러 운영
- 셀러 관리
- 셀러별 상품 검수
- 셀러별 정산

운영 설정
- 카테고리/브랜드 관리
- 성분 사전 관리
- 이미지 파일명 규칙 관리
- 엑셀 업로드 양식 관리
- 관리자 권한/로그
```

초기 화면에서는 셀러 운영과 운영 설정을 비활성/준비중으로 표시하면 된다.

### 5.3 상품 목록 컬럼

현재 상품 목록은 운영 상태 확인용 핵심은 있지만 팀장님 요구 컬럼이 일부 빠져 있다.

추가 필요:

- 썸네일
- 셀러명
- SKU
- 카테고리
- 전시상태
- 이미지 상태
- 성분 매핑 상태
- 최근 수정일
- 담당자
- 관리 버튼
- 엑셀 업로드 회차

### 5.4 엑셀 등록 미리보기

현재는 검증 후 성공/실패 요약에 가깝다. 팀장님 문서 기준으로는 DB 반영 전 미리보기 단계가 중요하다.

추가 필요:

- 업로드 대상 셀러 표시
- 정상 행/오류 행 분리 미리보기
- 등록 실행 버튼은 검증 통과 후 활성화
- 같은 셀러 내 `product_code` 중복 검증 표시
- 작업 로그에 seller_id, 파일명, 성공/실패 건수 표시

### 5.5 이미지 매칭 기준

현재 이미지 자동 연결 설명은 있으나, 팀장님 문서의 금지 조건을 더 강하게 표시해야 한다.

추가 문구:

```text
이미지 매칭은 product_code만으로 하지 않습니다.
반드시 seller_id + product_code 기준으로 매칭합니다.
```

### 5.6 재고/가격 단위

현재는 상품 단위 중심이다. 팀장님 문서는 SKU/옵션 단위 재고/가격을 요구한다.

보강안:

- 상품 row 아래 SKU row 표시
- `seller_id + sku_code` 기준 표시
- 같은 상품이라도 셀러별 가격/재고가 다를 수 있음을 명시

### 5.7 주문 상태 조회 범위

현재는 주문 상태 전이 mock 버튼이 있다. 팀장님 문서는 초기에는 주문 처리보다 상태 조회를 우선한다.

보강안:

- "조회 중심"으로 강조
- 주문 품목별 셀러 표시
- 취소/환불/반품 상태는 표시만 우선
- 상태 변경 버튼은 "원우 API 확인 필요" 또는 "로컬 미리보기"로 명확히 둠

### 5.8 상태값 표준화

팀장 문서 5절의 상태값 표를 기준으로 화면 어휘를 통일한다. 현재 프로토타입의 "검수필요"는 "검수대기"로, "품절임박"은 재고 부족 필터 기준으로 맞추고, 상품/이미지/성분/엑셀 상태가 대시보드·목록·검수 화면에서 같은 enum을 쓰도록 정리한다.

## 6. 다음 구현 순서 제안

디자인은 클로드 새 시안으로 교체하더라도, 기능 구현 순서는 아래처럼 잡는 것이 맞다.

### 다음 1단계: 관리자 셸 구조 보강

- 상단 현재 범위 표시: `본사 셀러`
- 로그인 사용자/권한 표시
- 메뉴 그룹화
- 준비중 메뉴 표시
- 모든 화면 공통으로 셀러 컨텍스트가 보이도록 정리

### 다음 2단계: 상품 조회/상태 확인 강화

- 상품 목록 컬럼을 팀장님 필수 컬럼에 맞춤
- 셀러 필터 자리 추가
- SKU 표시 추가
- 썸네일/카테고리/전시상태/담당자 추가
- 업로드 회차와 최근 수정일 표시

### 다음 3단계: 엑셀 업로드 흐름 강화

- 업로드 대상 셀러 표시
- 검증 결과 미리보기 화면 강화
- 정상/오류 행 분리
- 같은 셀러 내 상품코드 중복 검증 표현
- 등록 실행 전 확인 단계 추가

### 다음 4단계: 이미지 연결 흐름 강화

- `seller_id + product_code` 매칭 기준 표시
- 미매칭/중복/누락을 별도 탭 또는 섹션으로 구분
- 이미지 연결 확정 단계 명확화

### 다음 5단계: 성분 검수 강화

- 상품별 성분 원문과 매핑 후보를 같이 보여줌
- 성분 사전 검색 자리 추가
- 신규 성분 등록 요청 상태 추가
- 검수 이력 표시

## 7. Claude 새 디자인에 넘길 지시

디자인을 새로 뽑을 때 아래는 반드시 보존해야 한다.

```text
목표: 예쁜 관리자 랜딩이 아니라 상품 운영자가 반복적으로 쓰는 쇼핑몰 관리자 화면.

반드시 들어갈 구조:
1. 현재 운영 범위: 본사 셀러 / 추후 셀러 선택 가능
2. 사용자 권한: 플랫폼 상품 운영자 등
3. 메뉴 그룹: 대시보드 / 상품 운영 / 주문 운영 / 셀러 운영 / 운영 설정
4. 상품 목록은 seller_id + product_code / seller_id + sku_code 기준을 화면에 드러낼 것
5. 엑셀 업로드는 검증 -> 미리보기 -> 등록 실행 -> 성공/실패 리포트 흐름
6. 이미지 연결은 seller_id + product_code 기준 매칭
7. 성분 검수는 내부 ingredients.csv canonical 기준, exact만 자동 확정, 나머지는 pending
8. 재고/가격은 SKU/옵션 단위로 확장 가능해야 함
9. 주문은 초기에는 상태 조회 중심, 상태 변경은 API 계약 확인 후
10. 작업 로그와 변경 이력은 별도 운영 근거로 남을 것
```
