## 2. 7월 19일 완료 정의

7월 19일에는 모든 KPI가 반드시 목표를 달성해야 하는 것이 아니라, 아래 결과가 재현 가능하게 확정되어야 한다.

1. 평가 데이터와 테스트 조건이 version으로 고정돼 있다.
2. 추천 품질과 성능 결과가 실제 측정값으로 채워져 있다.
3. 목표 미달 항목도 원인·시도·남은 한계가 기록돼 있다.
4. 모든 발표 수치가 Git SHA, dataset/scoring version, 실행 결과에 연결된다.
5. 데모와 7분 발표를 중단 없이 수행할 수 있다.
6. PPT에 `[측정 전]`, 임시 문구, 검증되지 않은 완료 주장이 없다.
7. 포스터 디자인 원본·인쇄용 최종 파일과 전달 확인이 보관돼 있다.

## 3. 최종 책임 구조

역할 균형의 원칙은 다음과 같다.

1. 프론트 기능과 UI 품질을 분리한다.
2. 일반 API/DB 최적화와 추천 검색·scoring 최적화를 분리한다.
3. 측정 설계, 반복 실행, 최종 검증을 한 사람에게 몰지 않는다.
4. 모든 산출물은 최종 책임자 1명과 검증자 1명 이상을 둔다.

### 원우 백엔드 — 일반 API·DB 최적화 책임

주 산출물:

- 홈 전체 hydrate 제거와 일반 API stage/query 관측
- 상품 상세·인기상품 N+1, JOIN, 반환 row 최적화
- 일반 DB 인덱스와 `EXPLAIN (ANALYZE, BUFFERS)`
- 측정 결과에 근거한 Redis/application pool 적용 판단
- Cart/Checkout transaction 회귀 검증

KPI:

- 대상 API당 query 수·반환 row·DB time Before/After 기록률 100%
- 목표 endpoint p95·p99 개선 또는 미달 원인 확정
- 다른 핵심 API p95 회귀 10% 이내
- 기능 check 99% 이상, transaction 불변식 위반 0건

경계와 우선순위:

```text
P0 홈 hydrate 제거·stage/query 관측
P1 상품 상세/인기상품 N+1·일반 인덱스
```

- Elasticsearch/pgvector candidate retrieval과 scoring 최적화는 규태가 책임진다.

주 산출물:

- 추천 core stage 관측률 100%
- Recall@50을 함께 보존하며 candidate/scoring latency 개선 여부 판정

## 5. 공통 측정·보고 형식

모든 결과는 다음 형식으로 제출한다.

```text
산출물 이름:
책임자:
Git SHA:
dataset/scoring version:
테스트 환경:
측정 조건:
KPI 목표:
실제 결과:
PASS/FAIL:
원본 run/report:
실패 원인 또는 남은 한계:
다음 조치:
```

완료 판정은 문서 작성 여부가 아니라 다음 기준으로 한다.

- 재현 가능한 원본 결과가 있는가
- 목표와 실측값이 분리돼 있는가
- 실패도 숨기지 않고 설명되는가
- 다른 역할이 같은 조건으로 검증할 수 있는가

포스터 파일 전달은 다음 항목까지 함께 보관한다.

```text
파일 수신자와 연락처:
요구 크기·파일 형식:
파일명과 최종 수정 시각:
색상·여백·해상도·폰트 preflight:
전달 시각과 전달 방법:
수신·파일 열림 확인:
교정 확인자:
```

## 6. 매일 공유 형식

7월 11일부터 19일까지 매일 18시에 다음 네 줄만 공유한다.

```text
오늘 완료한 산출물:
실측 KPI와 PASS/FAIL:
```

blocker는 발견 즉시 관련 책임자와 PM에게 공유하고, 18시까지 기다리지 않는다.
